# 1. Introduction

## Overview

The database is the backbone of the Sagau marketplace. It stores user information, professional profiles, jobs, applications, agreements, reviews, notifications, and platform metadata.

Sagau uses **MongoDB**, a document-oriented NoSQL database, together with **Mongoose** to provide schema validation, relationships, middleware, and model abstraction.

The database is designed to support:

- Secure authentication
- Marketplace workflows
- Hiring lifecycle
- Reputation management
- Worker verification
- Future scalability

---

# Why MongoDB?

MongoDB was selected because it provides:

- Flexible document schema
- Horizontal scalability
- High performance
- Rich aggregation framework
- Excellent Node.js integration
- Rapid feature development

# 4. Database Design Principles

The following principles guide the database design.

---

## Separation of Authentication and Business Data

Authentication information is stored separately from business-specific information.

Example:

```text
User

↓

Worker Profile

↓

Professional Data
```

This prevents unnecessary duplication.

---

## Normalized References

Collections reference each other using ObjectIds.

Example

```text
Job

↓

Client ID

↓

ObjectId
```

instead of duplicating the full client document.

---

## Controlled Denormalization

Frequently accessed information may be duplicated when it improves performance.

Examples:

- Worker average rating
- Completed jobs count
- Trust score

These values are updated automatically through business logic.

---

## Immutable Historical Records

Historical records such as reviews and completed agreements should never be modified except through authorized administrative actions.

---

## Soft Deletion

Important entities should use soft deletion.

Example:

```text
isDeleted = true
deletedAt = Date
```

This preserves audit history.

# 14. User Collection

## Overview

The **User** collection is the master entity of the entire platform.

Every person who registers on Sagau first becomes a **User**.

Authentication, authorization, and account management originate from this collection.

Business-specific information (Client or Worker) is stored in separate collections.

---

## Purpose

The User collection is responsible for:

- Authentication
- Account Management
- Role Management
- Login Sessions
- Account Security
- Email Verification

---

## Relationships

```text
User

├── Client Profile

├── Worker Profile

└── Notifications
```

---

## Schema Structure

| Field         | Type     | Required | Description                |
| ------------- | -------- | -------- | -------------------------- |
| \_id          | ObjectId | ✓        | MongoDB Primary Key        |
| fullName      | String   | ✓        | User Full Name             |
| email         | String   | ✓        | Unique Email Address       |
| password      | String   | ✓        | Hashed Password            |
| role          | Enum     | ✓        | client / worker / admin    |
| profileImage  | String   | ✗        | Cloudinary Image URL       |
| phone         | String   | ✗        | Contact Number             |
| emailVerified | Boolean  | ✓        | Email Verification Status  |
| accountStatus | Enum     | ✓        | active, suspended, blocked |
| lastLogin     | Date     | ✗        | Last Login Timestamp       |
| createdAt     | Date     | ✓        | Created Timestamp          |
| updatedAt     | Date     | ✓        | Updated Timestamp          |

---

## Business Rules

- Email must be unique.
- Password is always hashed.
- Email cannot be changed without verification.
- Every user has exactly one role.
- A user cannot change roles after registration without administrative approval.

---

## Recommended Indexes

```text

role

accountStatus

createdAt
```

---

## Status Meaning

| Status      | Description            |
| ----------- | ---------------------- |
| OPEN        | Accepting applications |
| ASSIGNED    | Worker selected        |
| IN_PROGRESS | Agreement active       |
| COMPLETED   | Successfully finished  |

# 27. Job Business Rules

- Only Clients can create jobs.
- Worker cannot edit client jobs.
- Completed jobs cannot be edited.
- Cancelled jobs cannot receive applications.
- One job creates only one agreement.
- Client cannot hire multiple workers for the same job.

# 39. Review Rules

- One review per reviewer per agreement.
- Users cannot review themselves.
- Ratings must be between **1 and 5**.
- Editing reviews is allowed only within a limited period (e.g., 24 hours).
- Deleted reviews should be soft-deleted for audit purposes.
